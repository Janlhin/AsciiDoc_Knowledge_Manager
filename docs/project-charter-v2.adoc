项目名称：ADKM（ADOC Knowledge Manager）

项目类型：开源软件 / 本地优先知识库 / 跨格式文档关系管理

项目状态：立项提案（Proposed）

首期交付：Windows 桌面应用（Tauri 2）

核心定位：以 Markdown 与 AsciiDoc 双一等公民为格式基础、以统一引用图为产品核心的本地优先知识库。

本版相对 v1.x 的实质变更：交付形态由 VS Code 扩展改为桌面应用；实现策略由"从零构建"改为"以 Geode 为底座增量扩展"；产品价值由"关系图谱可视化"调整为"跨格式引用完整性校验"。

=== 0.2 已固定的技术决策

以下决策已依据实测或既有项目事实固定，不再作为开放选项：

. **交付形态为桌面应用。** 放弃 VS Code 扩展形态，理由见 ADR-0003。
. **技术栈跟随 Geode。** Tauri 2 + React 18 + TypeScript + CodeMirror 6 + Vite + Zustand。
. **以 Geode 为底座。** 保留其 UI 骨架与索引抽象，增量新增 AsciiDoc 解析器，不替换 Markdown 引擎。
. **AsciiDoc 解析采用 Asciidoctor.js 4.x。** 能力边界与分层策略见 ADR-0001。
. **解析上下文模型按 ADR-0002 执行。** include 归属、属性优先级、条件块求值均已固定。
. **首期不做 AsciiDoc 实时预览（L4）。** 理由见 4.2。

=== 0.3 命名说明

"ADKM" 名称中 "ADOC" 在 v2.0 定位下特指核心差异化格式，而非唯一格式。名称保留以维持认知连续性，对外介绍时应表述为"跨格式本地知识库"，不得表述为"AsciiDoc 专用编辑器"。

== 1. 项目背景

=== 1.1 现状与空白

本地优先知识库领域目前存在三个互不重叠的实现，各自覆盖一部分需求：

[cols="1,1,2,2"]
|===
|项目 |格式 |能力 |缺口

|Obsidian
|Markdown
|双链、反链、图谱、插件生态
|闭源；不识别 AsciiDoc；不支持属性化交叉引用

|Geode
|Markdown
|开源（Apache-2.0）；Tauri 桌面；Obsidian 插件兼容层
|不识别 AsciiDoc

|Luhmann
|AsciiDoc
|AsciiDoc 渲染、自动反链、图谱、断链报告
|不识别 Markdown；不支持 include / 属性替换 / 条件包含；不保存源码行号
|===

三者之间存在的空白是：**没有一个工具能让 Markdown 的 `[[wikilink]]` 与 AsciiDoc 的 `xref:\{attr}` 落在同一张关系图上。**

该空白在以下场景中具有实际影响：

. 同一团队内不同成员分别使用 Markdown 与 AsciiDoc 编写文档。
. 同一作者在不同时期使用了不同格式，需要统一检索与追溯。
. 技术规范类项目同时存在 Obsidian 笔记与技术文档。

=== 1.2 项目定位

ADKM 定位为**跨格式本地知识库**，其产品价值按优先级排列：

. **引用完整性校验**：解析并验证跨文档引用是否有效，包括目标文件、章节锚点、属性别名。
. **多版本一致性校验**：同一文档的多语言版本之间的结构对齐与版本号一致性。
. **统一关系图**：将不同格式、不同语法的引用归一为同一套关系模型并可视化。
. **编辑与预览**：在单一应用中进行格式原生编辑与渲染。

这不是一个"再做一个 Obsidian"的项目。图谱与双向链接是既有工具的共识能力，本项目不以此作为差异化；差异化在于**跨格式的引用语义统一与可校验性**。

=== 1.3 核心原则

[cols="1,2"]
|===
|原则 |要求

|格式原生
|不要求用户转换格式。Markdown 按 Markdown 语义解析，AsciiDoc 按 AsciiDoc 语义解析，两者不互相降级。

|引用可校验
|任何被识别的引用都必须可验证其有效性，并明确区分"有效""断链""未解析"三种状态。

|结果可重现
|相同输入与相同解析上下文必须产生相同的索引结果。不允许因实现细节导致差异。

|本地优先
|原始文档始终位于用户指定的文件夹，以纯文本形式存放，不引入专有数据库锁定。

|数据可重建
|索引、缓存、图谱均可从原始文档重建。用户自建的关系数据必须独立存储并可备份。

|上限可信
|无法支持的能力必须明确声明，不得以近似实现伪装成完整支持。

|底座可控
|基于第三方项目扩展时，必须明确记录上游版本、改动边界与升级策略。
|===

== 2. 目标、范围与非目标

=== 2.1 首期目标（P0）

. 打开本地文件夹作为工作区，索引 Markdown、AsciiDoc、TXT 三类文件。
. AsciiDoc 文件可渲染预览，可提取章节、交叉引用、属性、include。
. Markdown 文件保持底座原有能力，包括双链、反链、图谱、Obsidian 插件兼容。
. 建立跨格式统一引用模型，`[[wikilink]]`、`[text](path.md)`、`xref:`、`link:` 归一为同一套关系。
. 引用校验报告：逐条列出有效引用、断链、未解析目标。
. 多版本结构对比：识别同一文档不同语言版本的章节差异与版本号差异。
. 双向链接面板与全局/局部关系图。
. 文件变更监听与增量索引。

=== 2.2 后续目标

* 多工作区管理。
* 引用校验的自定义规则（如要求每篇文档必须有 `:revnumber:`）。
* AsciiDoc 的 include 组装视图。
* 文档模板与新建向导。
* 导出关系图为 JSON / DOT。
* Git 历史集成（查看文档的历史版本并对比）。
* 插件系统。
* 跨平台构建（macOS / Linux）。

=== 2.3 非目标

首期不开发：

* 实时协作（多人同时编辑）。
* 云端账号、同步服务。
* AsciiDoc 的实时内联预览（源码内渲染）。
* AsciiDoc 转 Markdown 或反向转换。
* 自研 AsciiDoc 或 Markdown 解析器。
* 自动修改用户原始文档内容。
* AsciiDoc 的 PDF / EPUB / DocBook 输出。
* Obsidian 插件在 AsciiDoc 文件上的兼容。

保留但降级的明确说明：

* Obsidian 插件兼容层仅在 Markdown 文件上生效，这是格式边界而非功能缺失。
* 关系图不作为主界面，作为校验结果的呈现方式之一。

== 3. 用户与场景

=== 3.1 目标用户

. 使用 AsciiDoc 编写技术规范的作者。
. 维护双语或多语言文档的团队。
. 同时使用 Markdown 笔记与 AsciiDoc 文档的个人。
. 需要审计文档引用完整性的项目维护者。

=== 3.2 典型场景

[cols="1,2"]
|===
|场景 |需求

|规范库维护
|大量 AsciiDoc 规范互相引用，需要确认引用目标仍然存在、章节未被改名。

|双语同步
|中文与英文版本需保持章节结构一致，需要定位未翻译或落后的章节。

|混合格式工作区
|个人笔记用 Markdown，正式文档用 AsciiDoc，需要统一检索与关系查看。

|重构前的引用审计
|重命名或拆分文档前，需要知道哪些文档引用了它。

|协作
|不同成员使用不同格式，需要在同一工具中打开对方的文件并理解其引用关系。
|===

== 4. 格式支持与解析分层

=== 4.1 支持矩阵

[cols="1,1,1,3"]
|===
|格式 |首期 |解析深度 |说明

|Markdown
|是
|完整
|沿用底座实现；支持 frontmatter、wikilink、标签、脚注、块引用、callout、数学、Mermaid；Obsidian 插件兼容层生效。

|AsciiDoc
|是
|L1–L3
|新增解析器；支持章节树、属性、交叉引用、include、内部锚点、预览；不提供实时内联预览。

|TXT
|是
|基础
|全文检索与预览，不解析结构。

|Canvas（.canvas）
|是
|结构解析
|解析 nodes / edges，映射为手工关系边，纳入关系图。

|HTML / PDF / DOCX
|否
|-
|列入后续；首期不索引。

|其他
|否
|-
|通过解析器适配接口扩展，接口形态在 7.2 定义。
|===

=== 4.2 能力分级 L1–L4

AsciiDoc 支持按四层递进定义，首期交付 L1–L3：

[cols="1,1,3,1"]
|===
|层级 |能力 |内容 |首期

|L1
|渲染
|预览面板渲染完整 HTML；内部链接可跳转；图片与附件可显示。
|是

|L2
|索引
|章节树与源码行号；`xref:` / `link:` 目标；document header 属性；`include::` 依赖；内部锚点。
|是

|L3
|编辑
|源码编辑，语法高亮；（可选）基于文本扫描的基础折叠。
|是

|L4
|实时内联预览
|在源码内直接渲染格式效果，隐藏或淡化语法标记。
|**否**
|===

L4 不作为首期的技术依据：CodeMirror 6 的 AsciiDoc 支持仅为 `StreamLanguage`（逐行 token 化），不提供语法树；而底座的实时预览实现完全依赖 Lezer 语法树。自建 AsciiDoc 语法树的工作量超出首期范围。

该取舍的对外表述为："AsciiDoc 采用源码与预览分栏工作方式"，而非"不支持实时预览"。

=== 4.3 AsciiDoc 解析分层边界

依据 ADR-0001，解析必须遵循四条边界：

[cols="1,1,3"]
|===
|编号 |约束 |说明

|D1
|块级结构只由解析器提供
|章节层级、表格、列表、代码块边界、源码行号，禁止用正则推断

|D2
|行内解析限定于块内容
|输入必须是块内容字符串，禁止对原始文件全文做无界定扫描

|D3
|块内容不用于结构判断
|块内容已剥离块标记，不得据此反推层级或边界

|D4
|误判必须降级
|无法确定的行内目标标记为"未识别引用"，不得抛异常或影响块级结果
|===

=== 4.4 解析上下文

AsciiDoc 的引用目标受 include、属性替换、条件包含影响，因此索引必须在显式上下文下进行。上下文的构成与默认值依 ADR-0002：

. 属性集：文档头属性优先，工作区默认属性兜底，内置默认最后。
. include 归属：被包含文件的引用归属其自身，另建 `includes` 边。
. 条件块：主干图只含无条件引用；条件引用单独存储并标记。
. 索引记录携带上下文指纹，指纹变更触发重索引。

=== 4.5 跨格式引用统一

所有格式的引用归一为统一模型：

[source,typescript]
----
interface LinkRef {
  targetDocId: string | null;   // 解析成功时为文档 ID，失败为 null
  rawTarget: string;            // 源文件中的原始写法
  sourceLine: number;           // 源码行号
  kind: "wikilink" | "markdown-link" | "xref" | "link-macro" | "include";
  reftext: string;              // 显示文本
  subpath?: string;             // 章节锚点或块 ID
  status: "resolved" | "broken" | "unresolved";
}
----

归一规则：

[cols="1,1,2"]
|===
|源写法 |kind |解析方式

|`[[Note]]` / `[[Note#h]]` / `[[Note\|alias]]`
|wikilink
|按文件名解析，支持别名与子路径

|`[text](path.md)`
|markdown-link
|按相对路径解析

|`xref:target.adoc#anchor[text]`
|xref
|先做属性替换，再按路径解析；记录锚点

|`xref:\{attr}[text]`
|xref
|从文档头属性表取目标；属性未定义则 `unresolved`

|`link:target.adoc[text]`
|link-macro
|按路径解析，与 xref 同等处理

|`include::path[]`
|include
|按上下文规则解析，产生 `includes` 边
|===

== 5. 核心功能

=== 5.1 引用校验（首期首要功能）

提供一份可导出、可定位的校验报告，包含三类结果：

[cols="1,1,3"]
|===
|状态 |含义 |判定条件

|有效
|目标存在且锚点存在
|`targetDocId` 非空，且 `subpath` 在目标文档中存在

|断链
|目标文件不存在
|路径解析完成但目标文件不在索引中

|未解析
|无法确定目标
|属性未定义、include 路径被拒绝、条件块外求值失败
|===

报告需支持：

* 按文档分组，显示每条引用的源码行号，可点击跳转到该行。
* 按状态筛选，按目标文档聚合（"哪些文档引用了已删除的 X"）。
* 导出为 AsciiDoc 表格或 JSON。
* 断链与未解析使用不同标识，不得合并为一类。

=== 5.2 多版本一致性校验

针对同一文档的多语言版本（如 `foo.adoc` 与 `foo-en.adoc`），提供结构对比：

[cols="1,2"]
|===
|检查项 |判定方式

|版本号
|比较 `:revnumber:`，不一致时报告双方版本

|章节数量
|比较各级标题总数，不一致时报告差值与层级分布

|章节结构
|按层级序列对齐，定位缺失或多余的章节（以标题文本相似度为辅助，不以文本完全一致为前提）

|行数偏差
|报告总行数差，用于提示内容规模差异
|===

对比结果以并列树呈现，缺失章节高亮。该功能不判断翻译质量，只判断结构是否对齐。

=== 5.3 双向链接与反向链接

* 显示当前文档的出链与入链，入链包含跨格式来源（Markdown 文档引用 AsciiDoc 文档需正确显示）。
* 目标不存在时显示为断链，点击可跳转到校验报告对应条目。
* 文档重命名或移动后更新索引。

=== 5.4 关系图谱

* 全局图：整个工作区的文档关系。
* 局部图：当前文档及指定深度的关联。
* 边类型区分：`links-to`、`includes`、`references`、`related-to`（来自 Canvas）、`broken`（断链）。
* 断链以独立样式呈现。
* 支持节点搜索、按格式筛选、按边类型筛选。

=== 5.5 搜索

* 文件名、标题、全文、标签、锚点、属性值。
* 支持按格式与状态（如"仅断链"）过滤。

=== 5.6 元数据

统一提取：

[cols="1,1,2"]
|===
|字段 |Markdown 来源 |AsciiDoc 来源

|标题
|frontmatter `title` 或首个一级标题
|文档标题（`= Title`）

|版本
|frontmatter `version`
|`:revnumber:`

|日期
|frontmatter `date`
|`:revdate:`

|标签
|frontmatter `tags` 或行内 `#tag`
|`:tags:` 属性

|别名
|frontmatter `aliases`
|无原生对应，可由工作区配置映射

|自定义属性
|frontmatter 全部键
|document header 全部属性
|===

=== 6.2 分层

=== 6.3 技术栈

== 7. 桌面应用设计

=== 7.1 界面

[cols="1,2"]
|===
|区域 |内容

|左侧栏
|文件树、搜索、标签、校验报告入口

|主区域
|标签页与分栏；每页可为编辑器、阅读视图、图谱、校验报告

|右侧栏
|反向链接、出链、大纲、文档属性

|底部状态栏
|索引状态、当前文件格式、引用状态摘要
|===

=== 7.2 编辑与预览

[cols="1,1,2"]
|===
|格式 |编辑 |预览

|Markdown
|源码 + 实时预览（底座能力）
|内联渲染

|AsciiDoc
|源码编辑 + 语法高亮
|分栏渲染，链接可跳转
|===

两种格式的编辑体验差异必须在界面上明确提示，不得让用户误以为 AsciiDoc 缺少功能。

=== 7.3 交互要求

* 键盘可操作，焦点可见，支持高 DPI 与深浅主题。
* 破坏性操作必须预览与确认。
* 索引与校验为后台任务，不阻塞编辑。
* 长任务（全量索引）显示进度与可取消。

== 8. Git 与版本管理

* 工作区可以是标准 Git 仓库，应用不修改 Git 配置。
* 首期只读：展示文件的提交历史、与上一版本的差异。
* 不自动提交、不自动推送、不执行破坏性 Git 操作。
* 索引重建不得修改原始文档。

自动版本记录属于独立项目范畴（Personal Git Vault），不在本项目中实现。

== 9. 非功能需求

=== 9.1 性能

[cols="1,2"]
|===
|项目 |目标

|冷启动
|空工作区不超过 3 秒进入可交互状态

|首次索引
|1,000 篇文档（平均 5KB）在 30 秒内完成

|增量索引
|单文件变更后 200ms 内更新索引

|引用校验
|1,000 篇文档的完整校验在 5 秒内完成

|图谱渲染
|500 节点流畅交互，超过时启用采样

|内存
|1,000 篇文档常驻不超过 500MB
|===

具体指标须在基准测试阶段以实测数据校正，校正结果记录于 ADR。

=== 9.2 稳定性

* 单个文档解析失败不得导致整体索引中断，失败项单独记录并在 UI 可见。
* 索引损坏可从原始文档重建。
* 文件监听必须处理重复事件与临时文件替换模式。
* 长时间任务可取消。

=== 9.3 安全

* 渲染不可信文档时限制脚本执行与外部资源加载。
* AsciiDoc 渲染禁用 `safe: unsafe`，include 路径限制在工作区内。
* 不擅自上传任何文档。
* 不执行文档中嵌入的 shell 指令。

=== 9.4 可维护性

* 核心模块无框架依赖，可独立测试。
* 上游 Geode 的改动边界记录于 ADR-0003，每次合并上游后更新。
* 关键行为有回归样本集（至少覆盖：属性未定义的 xref、跨格式引用、双语结构差异）。

== 11. 测试与质量

=== 11.1 测试类型

* 单元测试（解析器、校验器、归一化）
* 集成测试（索引 → 校验 → 图谱数据）
* 回归样本集（跨格式引用、属性边界、双语差异）
* 性能基准（1,000 篇文档）
* 端到端（打开工作区 → 编辑 → 校验 → 跳转）

=== 11.2 关键测试场景

. AsciiDoc 文档解析出正确的章节树与行号。
. `xref:\{attr}` 在属性已定义时解析为目标文件，未定义时为 `unresolved`。
. `xref:path.adoc#anchor` 在锚点存在时为有效，不存在时为断链。
. Markdown 的 `[[wikilink]]` 与 AsciiDoc 的 `xref:` 指向同一文档时，入链合并显示。
. include 的引用归属符合 ADR-0002，反链计数不随 include 次数膨胀。
. 双语文档章节数不同时，能定位缺失章节。
. 同一上下文下重复索引结果一致。
. 单文件解析失败不影响其余文档。
. 1,000 篇文档的索引与校验满足 9.1 的性能目标。

=== 11.3 质量门禁

合并前必须通过：类型检查、静态检查、单元测试、关键集成测试、构建。

== 12. 开源与许可证

=== 12.1 项目许可

建议采用 Apache-2.0，与底座一致，避免许可证组合复杂度。

=== 12.2 上游义务

fork Geode 产生的义务：

* 保留原 Apache-2.0 许可证文本。
* 在 `NOTICE` 中声明源自 Geode 及其版权信息。
* 修改过的文件需保留原版权声明，并注明修改。
* 不得使用 Obsidian 的名称、图标暗示官方关联。

=== 12.3 依赖审查

Asciidoctor.js、CodeMirror、d3-force 等关键依赖须记录许可证、维护状态与更新责任。Asciidoctor.js 4.x 为 2026-11-02 发布的新版本，须锁定次版本并建立升级回归。

== 13. 风险

[cols="1,2,2"]
|===
|风险 |影响 |应对

|上游合并成本
|Geode 为 active alpha，迭代快；改动其核心文件会持续产生冲突
|把改动集中在上游较少触及的文件；每次合并后记录冲突清单；必要时冻结上游

|AsciiDoc 行内解析误判
|引用校验出现假阳性/假阴性
|建立回归样本集；误判一律降级为"未识别"而非猜测

|双语对比误报
|标题文本不同导致对齐失败
|以层级序列为主、文本相似度为辅；允许人工确认对齐结果

|产品定位模糊
|被理解为"又一个 Obsidian"
|对外表述统一为"跨格式引用校验"，不以图谱为卖点

|性能不达标
|大工作区卡顿
|在 0.3.0 即引入 1,000 篇基准确认可行性

|解析上下文未覆盖真实场景
|引用归属与用户预期不符
|ADR-0002 的默认值须在真实规范库上验证，必要时调整
|===

== 14. 验收标准

首期正式发布必须满足：

. 能打开包含 adoc、md、txt 的工作区并完成索引。
. AsciiDoc 文件可预览，内部链接可跳转。
. 引用校验报告准确列出有效、断链、未解析三类结果，可定位到源码行。
. 跨格式引用在同一份入链列表中正确合并。
. 双语版本对比能定位章节差异与版本号差异。
. 关系图正确反映校验结果，断链有独立标识。
. 文件新增、修改、删除、重命名后索引正确更新。
. 索引可从原始文档重建。
. 单文件失败不影响整体。
. 不改动用户原始文档。
. 在 1,000 篇文档的基准上满足 9.1 的性能目标。
. 许可证与上游归属声明完整。

== 16. 立项决议

本项目正式进入立项评估阶段。

首期交付重点：

[IMPORTANT]
--
以 Tauri 桌面应用为唯一交付形态，以 Geode 为底座增量扩展 AsciiDoc 支持，以跨格式引用校验为产品首要价值。
