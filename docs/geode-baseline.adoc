= ADKM 相对 geode 的底座差异基线

:encoding: utf-8
:lang: zh-CN
:toc: left
:toclevels: 2

本文记录 **ADKM 相对其底座 geode 的差异**，用于每一次"还差多少 / 该做什么"的评估。

== 为什么需要这份基线

评估"ADKM 离目标还有多远"时，参照物必须是 **geode（底座）**，而不是 Obsidian（参照产品）。两者混用会导致两类错误判断：

* 拿 Obsidian 的功能广度去衡量 ADKM → 高估差距，把 Obsidian 十年商业演进的成果算成我们的欠债
* 拿 ADKM 的纵深能力去衡量 Obsidian → 低估差异化，看不见我们在 adoc 与引用校验上的领先

本文只记录**已核实的事实**与**明确标注的判断**，区分二者。

=== 差异的性质

[cols="2,3"]
|===
|类别 |性质

|**既有能力**
|**零删除。** 对 geode 原有文件的改动全部是「接入式」的——把 AsciiDoc 与 office 预览塞进既有的索引 / 图谱 / 预览管线，而非另起炉灶或重写。

|**新增能力文件**
|全部集中在 `src/` 下的**十二个新文件**，构成 ADKM 相对 geode 的**全部**产品增量：

[cols="2,3"]
|===
|文件 |带来的能力

|`core/parsers/asciidoc.ts`
|*AsciiDoc 解析器*

|`core/parsers/indexable.ts`
|跨格式统一索引入口

|`core/asciidoctorPreview.ts`
|Asciidoctor 懒加载渲染

|`styles/adoc-preview.scss`
|adoc 阅读视图样式

|`features/attachment/formatPreview.ts`
|格式注册表

|`features/attachment/DocxPreview.tsx`
|docx 预览

|`features/attachment/PptxPreview.tsx`
|pptx 预览

|`features/attachment/EpubPreview.tsx`
|epub 阅读器

|`features/attachment/XlsxPreview.tsx`
|xlsx 可编辑网格

|`core/product.ts`
|品牌占位与产品标识

|`styles.d.ts` / `format-shims.d.ts`
|类型声明（`?raw` 导入、mammoth）
|===

|**非能力增量**
|差异统计里的大头其实**不是能力**：样式层的 CSS→SCSS 机械改写、重命名与搬家、文档与根目录规范化。这些必须从「新增能力」里扣除，否则会严重高估工作量。

|**架构成熟度**
|缓存 / 增量 / 事件总线 / 状态真源——**底座为零，我们也是零**。见下文第三条结论。
|===

=== 结论

[quote]
____
保留 100% 既有能力（**未删除任何文件**），以**少量**真实产品代码换来两个 geode 完全不具备的维度：**AsciiDoc 全链路**与**多格式 office 预览**。

工程规范侧从 0 到有（SCSS 化、脚本 TS 化、五件套文档 + ADR 体系）。

**架构成熟度侧：0 进展**——缓存 / 增量 / 事件总线 / 状态真源，上游 geode 同样为零，我们同样为零。
____

这个「以少量代码接入而非重写」的形态说明两件事：

. geode 的底座质量不错；
. 剩下的路**不在写代码，在补架构**。

== 三条结论

=== 一、产品能力上已完成质变

从「md 编辑器」到「专业文档工程工具」，不是量变。ADKM 相对 geode 的增量集中在 charter 定义的方向上，且已在代码中落地——**代价是少量新增文件**，且未删除任何既有文件。

=== 二、工程规范上已建立体系

五件套文档、ADR、strict TS、脚本类型化——geode 上游没有这一层。

=== 三、架构成熟度是唯一的大缺口，且 geode 也没有

这一栏是 **0**，且底座同样为 **0**。

这一点必须说清：**geode 的作者从未做过 Obsidian 那个量级的缓存 / 索引 / 增量体系**。Obsidian 是十年商业演进的产物，geode 是个人项目的演进产物。所以用 REA 逆向 Obsidian **不是在补 geode 的短板——是在补一个 geode 从来没有过的维度**。

而这不是可有可无的工程洁癖：charter 承诺的「引用完整性校验优先」，在大库上若无缓存与增量索引，就是**不可用的功能**。承诺了却兑现不了，等于没承诺。

因此 REA 逆向是兑现产品承诺的技术路径，不是可选的锦上添花。范围与纪律见 `obsidian-reverse-engineering.adoc`。

== 待验证项

以下尚未实测，不得当作结论使用：

* 「重计算堵 UI 主线程是卡顿根因」——这是*假设*，无 profiling 数据支撑。
* L4 的 x-data-spreadsheet 网格与 epub.js 阅读器真实 DOM 渲染——仅构建与逻辑验证通过，未在真实 Tauri 运行下目视确认（ADR-0004 未设「复审条件」章节，该项待补）。
