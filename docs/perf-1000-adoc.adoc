:revnumber: 1.0.0
:revdate: 2026-11-27
:status: active

== 这份文档管什么

按章程 §9.1 的性能目标，对 1,000 篇平均约 5 KB 的 AsciiDoc 文档做可复现基准：
索引构建、全量引用校验、内存三项的实测数值，与目标逐条对照。

所有数字均来自 `scripts/adoc-1000-bench.ts` 的真实运行，**没有用估算或插值冒充实测**；
脚本、夹具生成方式、机器规格与复现命令都在本文留痕。

== 测量口径（先读这一节，避免把数字读大）

=== 测的是哪一层

- **索引构建**：TS 侧 `MetadataIndex.rebuildAll()`——内存夹具读取 + `parseDocument` 解析
  + 元数据表 / 名称映射重建。对应应用内「元数据索引」这条 TS 计算路径。
- **引用校验**：纯函数引擎 `auditVault()`——在已解析的 `meta.links` 上做
  `resolveLink` / `resolveXref` / `resolveInclude` 解析与 include 环检测。
- **内存**：Node 22 进程 `process.memoryUsage()`：`heapUsed` 为 V8 堆，`rss` 为常驻内存。

=== 不测哪一层（本报告数字不能外推到这些路径）

- **不含** Rust FTS5 持久化索引的 IPC 写入（`index_upsert` 等 Tauri 命令）；
- **不含** Asciidoctor.js 阅读视图渲染；
- **不含** WebView2 / Tauri 桌面进程占用；
- **不含**磁盘 IO：夹具全部在内存中构造（`MemoryVaultAdapter`）。

=== 夹具与统计

- 确定性 LCG（种子 42）生成 1,000 篇 adoc + 20 个 include 片段；每篇含标题层级、
  文档头属性、`xref:` / `link:` / `<<>>` / `include::` 引用，目标均按库内相对路径写，
  校验时 `broken-xref` / `broken-include` / `broken-link` 为 0。
- 每篇正文补齐到 ≥ 5,000 字符。同一 `--count` 下夹具逐字节一致，可跨轮次、跨机器复跑比较。
- 冷轮次：每轮全新 vault + 全新元数据索引后 `rebuildAll()`；热轮次：同一索引反复 `rebuildAll()`；
  校验在热索引上重复多轮。统计量取中位数与 p95（脚本 `summarize()` 实现）。

== 复现命令

前置：Node 固定在 `D:\Projects\_tools\node-v22.23.2`，先把它加到 `PATH` 最前；
`node_modules` 已 junction 到主仓，**不要** `npm install`。

[source, shell]
----
# 全量基准（冷 5 轮 / 热 7 轮，表格输出）
node scripts/adoc-1000-bench.ts --count=1000 --cold=5 --hot=7

# 机器可读输出（含逐轮样本）
node scripts/adoc-1000-bench.ts --count=1000 --cold=5 --hot=7 --json
----

类型门禁：`npm run typecheck`、`npm run typecheck:scripts` 退出码 0；
全量测试：`npm test -- --run`（基线 215 passed + 1 expected fail + 1 skipped，本分支不增减）。

脚本不写仓库内或仓库外的持久临时文件；进程退出即回收。

== 与章程 §9.1 目标对照

| 章程指标 | 目标 | 实测（聚合中位数） | 结论 | 余量 |
| --- | --- | --- | --- | --- |
| 首次索引 1,000 篇（平均 5 KB） | ≤ 30,000 ms | 130.44 ms（冷构建，TS 侧） | **达标** | 约 230 倍 |
| 全量引用校验 | ≤ 5,000 ms | 416.06 ms | **达标** | 约 12 倍 |
| 内存 | ≤ 500 MB | heapUsed 78.03 MB / RSS 179.41 MB | **达标** | heap 约 6.4 倍；RSS 约 2.8 倍 |

> 对照口径提醒：上表「实测」只覆盖第一节声明的 TS 侧计算路径。章程目标在桌面端的
> 完整口径（含 Rust 索引写入、WebView 占用）需要在 Tauri 真机上另测，本文不据此宣称端到端达标。

== 结论

1. 在本机 9800X3D 上，TS 侧索引构建与引用校验相对章程目标余量充足；
   三轮波动主要来自系统后台负载（引用校验 365.55 → 471.62 ms），未触及目标量级。
2. 内存增量温和：相对 baseline，结束时 heapUsed 增加约 24–38 MB，RSS 增加约 35–39 MB；
   RSS 大头是 Node + Vite SSR 运行时本身（baseline 已约 140 MB）。
3. 夹具引用全部可解析，校验引擎没有在「假失败」上消耗计时；告警项已单独归类。

== 已知局限

- **未测桌面路径**：Rust FTS5 持久化、Tauri 命令 IPC、WebView2 渲染与窗口占用均未纳入；
  端到端首次索引 / 校验耗时需真机复测。
- **合成语料**：文档结构规整、引用密度固定、无真实长文档、无深层 include 嵌套、无中文 prose；
  真实语料的解析与校验成本可能高于本基准。
- **JIT 预热**：冷轮次新建对象，但 V8 引擎在进程内已完成预热；与桌面冷启动的 JIT 状态不同。
- **机器相关**：绝对值绑定 9800X3D / 32 GB 内存，其它硬件不可直接搬用；相对余量结论可参考。
- **无磁盘 IO**：夹具在内存构造，未覆盖真实读盘与文件系统缓存效应。
- **告警噪音**：夹具不带 YAML frontmatter，`frontmatter-missing` 告警每篇一条；
  这不影响引用校验计时，但说明夹具不是完整 docs-as-code 样例库。
- **轮次波动**：三轮间中位数差异（尤其校验阶段）反映后台调度影响，单次运行不宜作为性能承诺。
