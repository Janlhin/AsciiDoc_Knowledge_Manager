决策类型：交付形态 / 实现基础 / 技术栈

影响范围：全局

本 ADR 记录两个相互绑定的决策：放弃 VS Code 扩展形态，以及选择 Geode 作为实现底座。二者不可分割——桌面形态是选择 Geode 的前提，选择 Geode 也锁定了技术栈。
--

== 1. 背景

立项书 v1.x 规定首期交付 VS Code 扩展，长期再迁移到独立桌面应用，核心引擎用 TypeScript 编写以兼顾两者。

在进入实现前，需要重新确认该路径，原因有三：

. 实测表明 AsciiDoc 的解析能力边界（ADR-0001）使得核心引擎的工作量高于原估算，而 VS Code 扩展形态对本项目的价值增益有限。
. 存在可复用的开源桌面实现（Geode），能显著缩短 UI 层工期。
. 协作方使用 Obsidian（Markdown），需要工具同时容纳 Markdown 与 AsciiDoc，而单一格式的专用工具无法满足。

== 2. 问题

需要同时回答两个问题：

*Q1*：首期交付形态是 VS Code 扩展还是独立桌面应用？

*Q2*：若为桌面应用，是从零构建，还是基于既有开源项目扩展？基准候选为 Geode、Nodum、Luhmann。

== 3. Q1：交付形态

=== 3.1 可选方案

[cols="1,3,2"]
|===
|方案 |说明 |主要缺陷

|A1 保持 VS Code 扩展
|首期交付扩展，核心引擎用 TS，长期再包一层桌面壳
|失去宿主提供的编辑器能力之外，同时要维护两套宿主适配；扩展无法提供全局关系图的主界面；Obsidian 兼容层无处安放

|A2 直接做桌面应用
|首期即为独立桌面应用，编辑器、文件树、图谱全部自持
|需要自建编辑器与基础交互，工期增加；但可控性最高

|A3 扩展与桌面并行
|两套形态同时维护
|单人/小团队不可行，核心引擎需长期维持两套适配层
|===

=== 3.2 决定

采用 *A2*。

=== 3.3 理由

. **产品形态决定界面结构。** 本项目的核心输出是"引用校验报告"与"跨格式关系图"，两者都需要占据主区域的大面积视图。VS Code 扩展只能通过 Webview 提供这类界面，而 Webview 与宿主的编辑器是分离的，用户需要在编辑器与 Webview 之间反复切换，交互成本高。
. **编辑器能力可获得替代。** VS Code 提供的语法高亮、多光标、搜索替换，CodeMirror 6 均可提供；AsciiDoc 的语法高亮通过 `StreamLanguage` 可实现。放弃 VS Code 并不等于放弃编辑器能力，只等于放弃"免费获得"。
. **协作场景要求同时容纳两种格式。** 协作方使用 Obsidian，若本项目是 AsciiDoc 专用扩展，协作方无法使用同一工具打开自己的文件。
. **A3 在资源约束下不成立。** 维护两套宿主适配的成本高于其收益。

=== 3.4 代价

* 需要自建文件树、命令面板、快捷键体系、主题系统。该部分由 Q2 的决策部分抵消。
* AsciiDoc 无法获得宿主级语法支持，编辑器体验弱于 VS Code + Asciidoctor 插件。此代价在 4.2（L4 不做）中进一步体现。

== 4. Q2：实现基础

=== 4.1 候选评估

[cols="1,1,1,1,3"]
|===
|候选 |栈 |规模 |许可 |评估

|Geode
|Tauri 2 + React 18 + TS + CM6
|51,954 行 TS/TSX + 821 行 Rust
|Apache-2.0
|技术栈与目标一致；UI 骨架完整；索引抽象格式无关

|Nodum
|FastAPI + Next.js + PostgreSQL + Redis + MinIO
|85,410 行
|MIT
|多租户 Web 服务，需数据库与对象存储，与本地优先原则冲突

|Luhmann
|Blaise Pascal
|4,681 行
|BSD-3-Clause
|唯一的 AsciiDoc 知识库实现，但语言无法进入 TS 生态
|===

=== 4.2 否决理由

*Nodum*：架构以服务端为中心，工作区数据存放于 PostgreSQL，文件内容与索引分离，需要 Redis 与 MinIO 支撑协作与存储。这与"原始文档始终位于用户文件夹"的核心原则直接冲突。改造为本地应用的工作量超过从零构建。

*Luhmann*：实现语言为 Blaise Pascal，代码无法在 TypeScript 项目中复用。但其设计与边界认知具有参考价值，具体包括：AsciiDoc 行内目标必须在块内容上扫描而非依赖解析器 AST；断链报告应作为独立页面；领域核心不感知 HTTP、文件系统与渲染器。上述三点已分别纳入 ADR-0001、立项书 5.1 与 6.2。

*补充说明*：Luhmann 的 `LICENSE` 为 BSD-3-Clause，但其 14 个源文件头均标注 `SPDX-License-Identifier: MIT`，存在许可证声明不一致。本项目不复制其代码，故不受影响；若将来需要移植其逻辑，须先向上游确认许可证。

=== 4.3 决定

采用 *Geode* 作为底座，fork 后在 `src/core/parsers/` 增量新增 AsciiDoc 解析器，不替换 Markdown 引擎。

=== 4.4 可复用性与改动边界（实测）

*扩展点*：

[cols="1,2"]
|===
|事实 |对方案的意义

|`parseNote(path, content)` 是纯函数入口
|只需在入口按扩展名分派，不影响既有调用方

|`NoteMetadata` 字段为格式无关抽象（links / tags / headings / blocks / footnotes / frontmatter / aliases）
|AsciiDoc 可映射到同一结构，图谱与面板无需改动

|全仓仅 4 处 `.md` 硬编码判断
|改动范围可控

|`src/compat` 与 `core`/`features` 基本隔离，仅 `app` 层 3 处引用
|Obsidian 兼容层可原样保留，且不污染核心

|图谱只消费 `GraphNode` / `GraphEdge`
|数据源可替换，渲染层无需改动
|===

*保留*：graph、explorer、workspace、backlinks、outline、search、palette、settings、compat、`core/markdown.ts`、`src-tauri`。合计约 25,000 行。

*修改*：`core/types.ts`、`core/metadata.ts`、`core/vault.ts`、`features/editor/cmExtensions.ts`、`features/editor/preview.ts`。约 60 行。

*新增*：`core/parsers/asciidoc.ts`、`core/parsers/canvas.ts`、`core/validate/refs.ts`、`core/validate/bilingual.ts`、`features/validate/`。约 1,500 行。

=== 4.5 技术栈锁定

跟随 Geode，不另行选择：

* TypeScript 5.x（strict）
* Tauri 2（Rust 侧仅桥接）
* React 18（不升级至 19，避免与上游合并冲突）
* Vite 6（跟随上游）
* CodeMirror 6
* Zustand（状态）
* markdown-it（Markdown 渲染）
* Asciidoctor.js 4.x（AsciiDoc 解析）
* d3-force（图谱）

*未选择 Wails + Svelte 的理由*：该组合与 Personal Git Vault 的技术路线一致，但会作废 Geode 的复用价值、现有 AsciiDoc 工具链的兼容性，以及协作者的 TypeScript 技能栈。Go 侧优势不足以抵消这三项损失。

== 5. 后续影响

=== 5.1 上游合并策略

Geode 处于 active alpha（v0.269.0），迭代频繁。为控制合并成本：

. fork 时固定到具体 commit，并记录该 commit 的哈希与日期。
. 改动集中在 `src/core/parsers/`、`src/core/validate/` 等上游不存在的路径，尽量减少对上游文件的修改。
. 必须修改的上游文件，改动处以统一注释标记（`ADKM:`），便于合并时定位。
. 每次同步上游后，更新本 ADR 的"上游版本"小节，并运行全量回归样本集。
. 若上游改动导致合并成本超过重写成本，触发重评（见 6）。

=== 5.2 许可义务

Geode 为 Apache-2.0。fork 后须：

* 保留 `LICENSE` 原文。
* 新建 `NOTICE`，声明本项目包含源自 Geode 的代码及其版权归属。
* 被修改的文件保留原版权头，并注明修改。
* 不得使用 Obsidian 或 Geode 的名称与图标暗示官方关联。

=== 5.3 能力上限的对外表述

由于底座以 Markdown 为一等公民、AsciiDoc 通过新增解析器支持，部分能力天然不对称：

[cols="1,1,1"]
|===
|能力 |Markdown |AsciiDoc

|源码内实时预览
|支持
|不支持（L4 不做）

|Obsidian 插件
|支持（compat 层）
|不适用

|结构化折叠
|基于语法树
|基于文本扫描
|===

对外必须明确表述该差异，不得暗示两者能力等同，也不得将 AsciiDoc 的缺失描述为"暂未支持"而给出不确定承诺。
