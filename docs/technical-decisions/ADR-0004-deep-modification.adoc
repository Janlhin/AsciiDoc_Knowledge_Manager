= ADR-0004：从最小增量改为深度改造
:revnumber: 1.0.0
:revdate: 2026-11-12
:status: accepted
:toc:
:toclevels: 2

== 状态

已接受。本 ADR 部分推翻 ADR-0003 的改造策略与上游合并条款，其余条款继续有效。

== 背景

ADR-0003 定的路线是「最小增量 fork」：保留 ADKM 约 25,000 行，修改约 60 行，新增约 1,500 行，只加 AsciiDoc 解析器，其余一概不动。该决策的前提是「尽量贴近上游，以便持续合并」。

2026-11-12 完成源码构建并实际运行后，前提发生变化。用户明确要求对 ADKM 做深度改造，使其成为目标产品，包括样式层在内的所有部分都可以改。同时确认了几项此前未核查的事实，使「最小增量」不再成立：

[cols="2,3,3",options="header"]
|===
|能力 |ADKM 实际现状 |后果

|AsciiDoc 支持
|无。仅有 `src/core/parsers/asciidoc.ts` 一个 193 行文件，尚未接线
|必须改 core 分派逻辑，不是加一个插件

|引用校验
|无
|整层从零

|双语对齐
|无
|整层从零

|Canvas
|无实现。`settings.corePlugin.canvas` 只是 i18n 文案，门后是空的
|整层从零，且是 `related-to` 关系的数据源

|Git 集成
|无。全仓无 `isomorphic-git`、`simple-git` 或 git 子进程调用
|整层从零

|中文界面
|有。`src/core/i18n/dict.*.ts` 已含中文词条
|可直接用，无需改造

|样式体系
|24 个纯 CSS 文件，7,828 行，无 Tailwind、无 CSS-in-JS
|需转 SCSS，规模可控
|===

结论：目标产品与 ADKM 现有能力之间的差距，不是「一个解析器」，是「六个新增层」。在这种差距下维持最小增量策略，只会导致大量代码写在上游文件里、每次 rebase 全面冲突——那时既没有上游收益，也没有干净的改造面。

== 决策

将策略从「最小增量 fork」改为「深度改造」，并同时采纳以下五条约束。

=== D1：改造分七层，层内自洽，层间可独立交付

[cols="1,2,3,2",options="header"]
|===
|层 |内容 |现状 |本层交付判据

|L1
|样式体系
|22/24 已转 SCSS，见 <<adr4-l1>>
|构建通过，规则集合与改造前等价

|L2
|AsciiDoc 解析与索引
|193 行解析器已写，未接线
|Blueprint 的 130 篇 adoc 出现在文件树与图谱中

|L3
|AsciiDoc 编辑
|无语言模式
|可编辑、可高亮、可保存，无语法树依赖

|L4
|引用校验与双语对齐
|无
|输出 213 条引用的三态报告与中英章节差异

|L5
|Canvas
|无
|可读写 `.canvas`，边映射为 `related-to`

|L6
|Git
|无
|可看状态、可提交、可拉取

|L7
|信息架构
|已有 tabs / 分屏 / 虚拟化文件树
|按文档工程语义调整导航，不重写
|===

样式层与兼容层的取舍另见 D2 与 D6。

**层间顺序不可随意调换**：L2 必须在 L4 之前，因为校验的数据源是索引；L1 放在最前，因为它不改变功能，能最早验证构建回路是否可靠。

=== D2：SCSS 三条硬规则

这三条不是风格偏好，是防止破坏现有主题机制的硬约束。

[cols="1,3",options="header"]
|===
|规则 |原因

|**R1** `theme-bridge.css` 与 `export.css` 永不转 SCSS
|两者通过 Vite `?raw` 以原文注入 `<style>`。转成 SCSS 后 `?raw` 拿到的是未编译源码，样式会整体失效

|**R2** `:root` 与 `html[data-theme]` 里的调色板字面量保持 CSS 自定义属性，不转 SCSS 变量
|两个原因：① Obsidian 主题在运行时通过 body 与 `.theme-dark` 作用域覆盖这些变量，编译期变量会切断覆盖链；② `theme-bridge.css` 头部有显式同步义务，要求调色板字面量与 app 中的逐字一致，改成 SCSS 变量会让这条约束无法用 grep 校验

|**R3** SCSS 只用于作者层：嵌套、mixin、`@use` 共享片段；`var(--x)` 一律保留
|同上。变量化的边界是「编译期常量」，不是「运行时主题令牌」
|===

允许且鼓励的 SCSS 用法：父选择器嵌套、`&-suffix` 生成同级类名、`@mixin` 消除重复（滚动条、浮动面板、按钮）、`@use` 拆分 partial、`@media` 内联嵌套。

=== D3：上游策略由「持续合并」改为「冻结 + 摘取」

ADR-0003 定的是固定 commit + 定期 rebase。深度改造后该条款失效：L2 至 L7 都会修改上游核心文件，rebase 必然大面积冲突，冲突解决成本高于自己重写。

新策略：

. 锁定当前 commit 作为基线，不再跟进常规提交。
. 上游修复按需摘取：只 cherry-pick 安全修复与解析正确性修复，每次摘取记录来源 commit。
. 停止把改动尽量塞进上游文件的做法。凡上游文件必须改，改在最小接缝处并加 `ADKM:` 注释；凡可新建，一律新建在 `src/adkm/` 下。
. 每季度评估一次上游是否已实现我方已有能力；若已实现且质量更高，反向替换。

=== D4：每层必须保持可运行

深度改造最大的失败模式不是技术难题，是改到一半没有可运行版本，最后无人敢合。

因此规定：任何一层完成后，`npm run build` 必须通过，`adkm.exe` 必须可启动并打开一个 vault。不接受「先拆完再修」的分支状态超过一天。

=== D5：样式改动必须给出规则集合 diff

机械转换（改名、拆分、嵌套化）要求**规则集合等价**：规则数不变，声明值不变，仅允许空白差异。本次 L1 的转换即按此判据验收，结果见 <<adr4-l1>>。

有意的视觉改动不受此约束，但必须单独一次提交，并在提交信息里写明改了哪些视觉决策。

=== D6：保留 Obsidian 插件兼容层

`src/compat/` 共约 10,397 行，占上游代码的 20%，是唯一的大块可删项。2026-11-13 决定保留。

理由：该层使产品能加载 Obsidian 社区插件与主题，属于差异化能力，不是历史包袱。它与 AsciiDoc 无冲突——兼容层只处理 Markdown 文件，adoc 走独立解析路径。

代价需要明确记账：这 10,397 行在深度改造中不会被重写，但会被持续维护。每一次上游 API 变动、每一个新版本 Obsidian 插件使用的 API，都可能需要在这里补齐。它是一份长期负担，且没有上游可以依赖（上游自 2026-07-04 起停更）。

因此附带一条约束：**任何对 `src/compat/` 的改动必须独立提交**，不得与 adoc、校验、Canvas、Git 等层的改动混在同一次提交里。目的是让这份负担的成本可度量——如果某段时间兼容层的提交占比过高，说明它在拖累主线，需要重新评估去留。

[[adr4-l1]]
== L1：样式层为何必须先做

它不是最有价值的一层，但它是最安全的验证样本：不改变任何功能，却能完整跑一遍「改源码 → 构建 → 比对产物 → 确认无回归」的回路。这个回路通了，后面六层才有可靠的验收手段。

=== 尚未完成

当前 22 个 `.scss` 文件的内容仍是原 CSS，只改了扩展名。这是**工具链就绪**，不是**SCSS 化完成**。

真正的 SCSS 化包括三步，按文件逐个进行：

. 抽公共 mixin（滚动条三处重复、浮动面板两处、按钮两处）
. 同前缀规则收进父级嵌套，用 `&-` 生成同级类名，必须保证编译后选择器不变
. 调色板以外的编译期常量（间距、圆角、层级、动画时长）提为 `$` 变量；调色板按 R2 不动

=== 一个必须记录的产物问题

`src/core/blueprint-seed.ts` 是 1.3 MB、139 行的未跟踪文件，内容是 Blueprint 部分文档的全文内嵌，由早期脚本 `scripts/gen-blueprint-seed.mjs` 生成。**全仓无任何引用**，属死代码。

它有两个害处：把用户文档内容混进源码目录；让任何全文检索都被这 1.3 MB 干扰。建议删除，或移出 `src/`。本 ADR 记录此事，处置另行确认。

== 下一步

按 D1 的顺序，L1 的工具链已完成，L2 是唯一该动的层。

L2 的具体动作只有三步，且都不需要改上游核心逻辑的大段代码：

. `src/core/metadata.ts` 的 4 处 `.md` 判断改为 `isIndexable(path)` 分派
. `src/core/vault.ts` 的 `getMarkdownFiles()` 改为 `getIndexableFiles()`
. 用 Blueprint 的 130 篇 adoc 验证 `parseAsciiDoc` 产出的 `NoteMetadata` 是否正确（章节、xref、行号）

验收判据：打开 Blueprint 作为 vault，130 篇 adoc 出现在文件树与图谱中，与 285 篇 md 落在同一张图上。
