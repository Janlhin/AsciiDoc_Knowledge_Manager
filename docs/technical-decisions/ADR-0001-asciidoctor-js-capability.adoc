== 1. 背景

章程 §5.2 建议采用 Asciidoctor.js 作为 ADOC 解析器。§4.2 同时要求：

* 必须区分文档源代码、解析结果和最终 HTML。
* 禁止直接使用不受控的正则表达式代替完整 AsciiDoc 解析器。

进入 0.2.0（基础框架）之前，必须先确认该解析器能否支撑以下四项能力，否则后续里程碑建立在未验证的假设之上：

. 块级结构与源码行号的对应关系：支撑预览定位、错误提示、关系跳转（§4.3、§5.3）。
. 行内链接目标的提取：支撑双向链接与关系图谱（§4.4、§4.5）。
. 解析结果与渲染结果的复用：支撑索引与预览共用一次解析（§9.1）。
. 解析失败与不可信内容的隔离：支撑稳定性与安全性条款（§9.2、§9.3）。

本 ADR 记录实测结论，并据此确定解析分层策略。

== 2. 问题

实测表明 Asciidoctor.js 4.x 的 AST 只暴露块级节点，不暴露行内节点。这意味着章程 §4.2 的字面要求（用完整解析器取得全部结构）在现有 API 下无法执行。

因此必须在三条路径中选择一条：

. 自行实现完整的 AsciiDoc 行内解析器。
. 放弃行内链接提取，接受 §4.4 与 §4.5 无法实现。
. 采用分层策略：块级由 Asciidoctor.js 提供，行内在块内容上受控解析，并严格界定"受控"的含义。

同时需确认 4.x 的接口形态（模块格式、同步性）是否会反向约束核心引擎的接口设计。

== 3. 实测结论

测试样本包含章程正文（1,162 行 / 27,194 字节）与合成的多文件工作区。

[cols="2,1,3"]
|===
|验证项 |结果 |证据

|样本可解析性
|通过
|`asciidoctor -v` 零警告；输出 93,911 字节 HTML；单次耗时 41 ms

|块级源码行号
|通过
|495 / 495 块节点均返回 `getSourceLocation()`；抽样 L28「1. 项目概述」、L30「1.1 项目背景」，与源码逐行一致

|章节树提取
|通过
|63 个 section，level、id、title、行号全部正确

|解析与渲染复用
|有条件通过
|`loadFile()` 得到 Document，`document.convert()` 返回 HTML；但模块级 `convert()` 不接受 Document 入参

|行内节点遍历
|**不通过**
|`block.getInlineNodes` 方法不存在；`catalog.links` 恒为空数组；`document.getLinks()` 返回 `[]`

|行内目标提取
|有条件通过
|`await block.getContent()` 返回块文本，在其中扫描 `xref:` 得到 2 处，与源码完全一致

|include 跨文件归属
|通过
|被包含块的 `getSourceLocation().getFile()` 指向被包含文件；行号指向该文件内的行

|属性驱动 include
|通过
|`include:\{chapter\}.adoc[]` 在属性于文档头定义时可正确解析

|路径穿越防护
|通过
|`safe: unsafe` 下 `include::../../../../Windows/win.ini[]` 被 jail 机制拦截，无内容泄漏

|解析器级增量
|**不支持**
|无增量 API；每次解析均处理整篇文档

|批量性能
|通过
|100 篇小文档解析 79 ms；27 KB 文档单篇 41 ms
|===

接口形态（影响核心引擎契约）：

* 纯 ESM（`"type": "module"`），无 CJS 构建产物。
* 全异步：`load()`、`loadFile()`、`block.getContent()`、`document.convert()` 均返回 Promise。
* `engines.node` 声明为 `>=20`（官方文档写 22，实际包声明更宽松）。
* `sourcemap: true` 必须显式开启，否则块级不返回源码定位。

== 4. 可选方案

=== 4.1 方案 A：自研完整 AsciiDoc 解析器

*优点*：完全控制 AST 形态，可同时暴露行内节点与源码定位。

*缺点*：AsciiDoc 的语法复杂度显著高于 Markdown —— 属性替换、属性条目、条件包含、include 递归、表格与列表的多层嵌套、块锚点与后置属性。完整实现的工作量以人年计，且与 §5.2 的选型建议直接冲突。解析器本身的缺陷会成为项目最大的不确定性来源。

*结论*：否决。

=== 4.2 方案 B：单一来源，放弃行内提取

*优点*：实现最简，无重复解析，无两套语法理解不一致的风险。

*缺点*：无法建立任何关系边，§4.4 双向链接、§4.5 关系图谱、§15 验收标准第 4 至 6 条全部无法满足。项目核心价值消失。

*结论*：否决。

=== 4.3 方案 C：分层策略（块级 Asciidoctor + 行内受控解析）

*优点*：满足全部功能需求；行内解析范围被块边界限定，输入是已剥离块标记的纯文本，可分析面显著收窄；块级结构无需重复实现。

*缺点*：需要明确"受控"的边界，否则退化为 §4.2 所禁止的全文本正则扫描；两套逻辑需对同一语法的理解保持一致，需建立回归样本集。

*结论*：采纳。

== 5. 最终决定

采纳方案 C，并以以下边界作为不可协商的实现约束。

=== 5.1 分层边界

[cols="1,1,3"]
|===
|编号 |约束 |说明

|D1
|块级只由 Asciidoctor.js 提供
|章节层级、表格结构、列表嵌套、代码块边界、源码行号，禁止用正则推断

|D2
|行内解析的输入限定为块内容
|输入必须是 `await block.getContent()` 的返回值；禁止对原始文件全文做无界定扫描

|D3
|块内容不得用于结构判断
|`getContent()` 已剥离块标记，不得据此反推章节层级或块边界

|D4
|行内误判必须降级
|无法确定的行内目标降级为「未识别链接」，不得抛出异常，不得影响块级结果
|===

=== 5.2 接口形态约束

[cols="1,2"]
|===
|编号 |约束

|I1
|核心引擎的解析入口必须声明为异步（`Promise<void>` 或等价形式），不得设计同步包装

|I2
|包格式为 ESM；CJS 宿主（如部分 VS Code 扩展打包形态）通过动态 `import()` 调用，不得依赖 `require`

|I3
|Node.js 运行时下限为 20；VS Code 扩展须锁定 `engines.vscode` 并验证宿主 Node 版本满足该下限

|I4
|复用解析结果一律调用 `document.convert()`；不得向模块级 `convert()` 传入 Document 对象
|===

== 6. 决定理由

. **功能可行性优先于实现纯度。** 方案 C 是唯一能同时满足 §4.4、§4.5 与 §15 验收标准的路径，且不引入自研解析器这一量级的技术风险。
. **"受控"是可界定的。** 行内解析的输入已被块边界裁剪为纯文本片段，其语法子集（xref、link、image、include 指令、行内锚点）可枚举、可测试。这与对原始文件做全文正则扫描有本质区别，不违反 §4.2 的立法意图。
. **接口异步性是早期不可逆的决定。** 全异步会渗透到索引引擎、缓存层、文件监听的每一处调用链。若在 0.5.0 之后才发现，返工成本远高于在 0.2.0 定案。
. **源码行号已验证可用。** §5.3 要求统一模型保留源文件定位信息，该项是硬需求。495 / 495 的通过率使其不再构成风险。

== 7. 后续影响

=== 7.1 对章程的修订

已同步修改：§4.2（两层策略）、§4.4.1（解析上下文）、§5.2（接口性质）、§9.1（增量粒度）、§11.2（测试场景）、§14（风险项）。

=== 7.2 对实现的约束

* 0.2.0 的解析接口契约必须在动工前定稿，且为异步形态。
* 需建立「行内解析误判」回归样本集，覆盖：嵌套在表格单元格内的 xref、列表项内的行内锚点、含属性引用的 link 目标、被转义的 `+xref:...+`。
* 索引结果需记录所用 Asciidoctor.js 的版本号，便于升级后定位行为差异。
