= 主线程成本审计与搬迁方案
:日期: 2026-11-16
:状态: 提案（T-062，待裁决后再实施）

== 一句话结论

这个应用**没有任何 Web Worker**，所有解析、解压、编码都发生在唯一能响应输入的线程上。而在大文件这条链上，**"把字节搬进来"比"解析它"更贵**：一个 144 MB 的 PDF/EPUB，光前端解码就要 300 ms 级的主线程时间（实测见下）。所以搬迁顺序应该是**先去掉传输税，再把解析搬进 Worker/Rust**——而不是先上 GPU。

== 判定标准

一项工作算"主线程成本"，须满足其一：① 同步占用主线程 ≥ 16 ms（一帧）；② 持有大块内存并在主线程做逐字节/逐元素处理；③ 触发多次布局/重绘。GPU 只加速"绘制"，对 ①② 无效；多核只有在**Worker 或 Rust 线程**里才用得上。

== 实测基线（release 构建，本机）

|===
| 场景 | 实测 | 方法

| 打开 60 MB PDF（闸门修复前）
| 首绘 112 ms 后 **72 ms + 151 ms** 阻塞
| rAF 帧间隔探针 + 220 ms 对照

| 打开 51 MB 真实 EPUB（库中《穷查理宝典》）
| 外壳挂载 101 ms，随后 0.6–17 s 内 **10 次 >50 ms**，累计约 **730 ms**
| 同上

| 启动恢复 8 个笔记标签 + 800 条笔记的库
| 无 >50 ms 帧间隔
| 同上

| **144 MB 二进制的 JS 侧解码**
| `atob` **106 ms** + 逐字节循环 **216 ms** ≈ **322 ms**；中间字符串 **201,326,592** 字符
| 页面内基准（`atob` + `charCodeAt` 循环，即 `vault.readBinary` 的现有实现）
|===

最后一行是本次审计最重要的发现：`vault_read_binary` 在 Rust 侧 `base64` 编码，前端 `atob` 后再**逐字节 push 进 Uint8Array**。这 322 ms 与文件大小线性相关，且**每次**打开大文件都要付。

== 不能搬 / 不该搬

* **React 渲染与 CodeMirror 输入**：必须在主线程（DOM/输入法）。
* **epub.js 的 iframe 排版**：iframe 里的布局由浏览器决定，搬不走；能搬的是它**前面**的解压。
* **PDF 查看器**：已经在独立进程（Chromium 内置），这也是为什么 144 MB PDF 打开后滚动不卡——卡的是我们喂给它的那一步。
* **原生对话框 / 剪贴板 / 菜单**：Tauri 侧，本就异步。

== 三阶段计划

=== P0：去掉传输税与主线程解压（收益最大，风险最低）

. **P0-1 原始字节 IPC**：`vault_read_binary`、`vault_write_binary`、`vault_read` 的大文件变体改用 `tauri::ipc::Response`（v2 提供）。前端 `readBinary` 直接返回 `Uint8Array`，删掉 `atob` 与逐字节循环。
   * 预期：144 MB 读取省 **≈322 ms** 主线程 + 约 200 MB 临时字符串。
   * 验收：同一 144 MB 文件，`readBinary` 前后各测一次，探针记录主线程阻塞时长；帧间隔无 >50 ms。
. **P0-2 EPUB/PPTX 解压移到 Rust**：新增 `unzip_list` / `unzip_read`（只解到内存或缓存目录，写入仍受 `assertSafeRelPath` 约束）。前端只请求当前章节的 HTML/CSS/图片。
   * 预期：51 MB 书的 730 ms 掉帧降到首章级（几十 ms）。
   * 验收：同样用 rAF 探针量"打开到首章可读"；E2E 增加"大 EPUB 打开无 >50 ms 帧间隔"。
. **P0-3 备份 ZIP 移到 Rust**：`zip` crate 在 Rust 线程打包，前端只显示进度。
   * 预期：备份期间界面可交互。
   * 验收：650 MB 库备份时，主线程无 >50 ms 帧间隔。

=== P1：解析进 Worker

W-1 `DocxPreview`（mammoth）、W-2 `XlsxPreview`（SheetJS 解析部分）、W-3 `asciidoctorPreview`、W-4 索引重建。
统一做法：`new Worker(new URL("./x.worker.ts", import.meta.url), { type: "module" })` + `postMessage` 传输 `ArrayBuffer`（零拷贝），Worker 只回传结构化数据（不要回 DOM 片段以外的重对象）。
风险：mammoth 的浏览器构建对 DOM 有依赖，需在 Worker 里实测；不行则退回 Rust（`docx-rs`）。

=== P2：图谱与渲染

* 布局进 Worker；或直接把迭代数按节点数做上限（`O(n)` 采样）。
* 绘制若仍是 canvas 2D 且节点数上千，再考虑 WebGL——**这是唯一值得谈 GPU 的地方**。

== 测量方法（可复现）

* 帧间隔探针：`Page.addScriptToEvaluateOnNewDocument` 注入 rAF 计时间隔，末尾用 220 ms 忙等**做对照**（WebView2 的 `longtask` API 在本机不触发，别再依赖它）。
* 阶段耗时：`__geodePerf`（已有 `metadataIndexMs` / `graphBuildMs`），本轮新增 `bootPhase*` 与 `binaryDecodeMs`。
* 任何性能改动必须先有"改前"数字，改后同夹具复测——这条已经在 D-028/D-029 里成为惯例。

== 我不建议做的事

* **上 WebGPU/WebGL 解决"打开大文件卡"**：两者都不处理 IO 与解压，改了也不会快。
* **把 ECharts/D3 之类整库换掉**：换库不改变"在哪个线程"。
* **调 JIT/打包体积**：发布包已 9.9 MB，解析耗时不是当前瓶颈。

== 建议的下一步

先做 **P0-1 + P0-2**：一个改 IPC 形态，一个把 EPUB 解压搬走。这两项合计覆盖你实际遇到的"大 PDF/大 EPUB 卡顿"的绝大部分，且不动任何 UI 语义。P0-3（备份）放在其后，因为它只在手动备份时发生。

== 行业实现对照（读源码，不是看宣传）

=== epub.js：整本入内存，但有"目录模式"这个后门

`src/archive.js`（已核对）：

* `Archive.open(input)` = `JSZip.loadAsync(input)` —— **整本书一次性进 JSZip**，解压后的所有条目留在 JS 堆里。
* 取单个资源走 `getBlob(url)` → `entry.async("uint8array")` → `new Blob` → `URL.createObjectURL`，结果缓存在 `urlCache`。
* `Book.open(input, what)` 的 `what` 支持 `binary / base64 / epub / opf / directory`。**只有前三者把 `archived = true`**，此时资源从 JSZip 取；`opf` 与 `directory` **不设 archived**，资源统一走 `this.request`（可被 `settings.requestMethod` 覆盖）逐个请求。
* 于是有一个明确的注入点：

[source,js]
----
ePub(url, {
  openAs: "directory",           // 走 openContainer → OPF → manifest，不解压
  requestMethod: myFetcher,      // 我们自己实现：命中 Rust 解压缓存
  replacements: "blobUrl",       // 非归档模式下默认是 "base64"，会把每章内联成 data URI（更重）
});
----

`myFetcher(url)` 只需返回文本或二进制：我们可以让它读 Rust 侧已解压到缓存的同名文件。**这样 epub.js 只在我们翻到某一章时才请求那一章**，既没有 51MB 的 JSZip，也没有整本解压的主线程成本。

=== pdf.js：worker 解析 + 只渲染可见页

`web/app.js` 里 `GlobalWorkerOptions` / `PDFWorker` / `PDFRenderingQueue` 说明它的两条核心策略：

. **解析在 Worker**：主线程只做 DOM/画布合成，PDF 的 xref、对象流、字体解码都在 worker 线程。
. **按需渲染**：`PDFRenderingQueue` + `RenderableTextLayer` 只为视口内的页分配画布；离屏页只保留占位。
. 网络侧还有 `rangeChunkSize` / `disableAutoFetch` / `disableStream`（走 HTTP Range 拉片段，而不是整份下载）。

对我们来说：**PDF 不需要换成 pdf.js**。WebView2 的 `<embed type="application/pdf">` 本身就是 Chromium 的 pdfium，**已经在独立进程里**，这正是 144 MB 打开后滚动不卡的原因。我们付的代价只在于"把 144 MB 交进去"这一步——那属于 P0-1（原始字节 IPC），不属于渲染。

=== 其他阅读器怎么做的

[cols="2,4,3",options="header"]
|===
| 项目 | 做法 | 对本项目的可借鉴性

| Thorium / Readium（桌面阅读器）
| 导入时**预解压**到本地缓存，运行时通过自定义协议把资源喂给渲染层；不把整本书放进 JS 堆
| **高**：与 P0-2 完全同构（Rust 解压 + 协议/请求函数）

| Kavita（自建书库）
| 服务端解压并做页码化图片流，前端只请求当前页
| 中：它是服务端形态，但"资源和渲染分离"的思路一致

| koodo-reader（Electron）
| 直接 `epub.js` + `pdf.js`，整本入内存
| 低：它和我们现在的实现是同一个毛病，只是主线程预算更宽裕（桌面 Chromium）

| calibre 自带查看器
| 本地解压 + 逐资源加载
| 中：同上，属"解压前置"路线
|===

**结论**：行业里没有谁靠"上 GPU"解决大书打开慢；共识是**把解压从渲染线程拿开，并且只按需取资源**。

=== P0-2 的精确改法（据上面源码定稿）

. Rust 新增 `epub_extract(vault, path)`：用 `zip` crate 解到 `<appdata>/epub-cache/<sha1(mtime+size+path)>/`，返回缓存根与 OPF 相对路径；同一指纹命中则直接复用。
. 前端拿到缓存根后：`ePub(cacheUrl, { openAs: "directory", requestMethod, replacements: "blobUrl" })`。
. `requestMethod(url)`：把 epub.js 解析出的相对路径映射到缓存文件，经 Tauri 的资源协议（`convertFileSrc`）或自注册协议取回；命中不到就退回 `app.vault.readBinary`（兜底）。
. 缓存清理：读取时更新 `lastUsed`，启动时按 LRU 删到上限（例如 1 GB），**只动缓存目录，不碰库**。
. 验收：51 MB 那本书，"打开到首章可读"的主线程阻塞从 ≈730 ms 降到无 >50 ms 帧间隔；翻章时每次只多一次单文件读取。

风险：① 资源协议需要在 Tauri 侧开放缓存目录的 scope（CSP/权限要单独验证）；② 有些 EPUB 用相对路径 + 锚点混合，`requestMethod` 需按 `Url.resolve` 语义处理编码；③ `directory` 模式不做整本完整性校验，损坏包会在翻到某章时才报错（需把错误映射成可读提示）。
